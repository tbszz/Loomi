# STAR 示例与 oversight 诚实规则

`interview-prep` 持 STAR 示例（T8 §5：面试题库 + 考察点 + STAR 示例归本 skill）。
示例是 few-shot，不是范文——**结构可学，事实必须换成候选人自己的**。

## 硬规则：oversight 只能讲成 led-not-performed

参数表 `skill_requirements` 四级门槛（T14 Q5）：

| 级 | 含义 | 可否作 hands-on 声称 |
|---|---|---|
| `deep` | 独立做过生产环境关键决策 | ✅ strong |
| `working` | 生产中日常使用，能独立完成任务 | ✅ stated |
| `oversight` | **团队做、我 review / 定方向** | ❌ 只能 led-not-performed |
| `historical` | 学过/用过但已过时或很浅 | ❌ Miss，不得声称 |

`oversight` 级的经历**不是不能用**，而是必须按"我定方向、我 review、我担责"讲。
把它讲成"我亲手做的"就是责任范围通胀（T6 Q6 四类越界之一），当前求职工具的证据校验 会拦。

T6 Q6 的校验口径：ownership 动词（`led` / `owned` / `独立负责` / `主导` / `牵头`）只在 Fact 有明确
ownership 证据时允许；"参与"不得扩为"负责"。**这条由代码执行，本文件不重复定义。**

## 例 1：正确的 oversight 讲法

场景：候选人定了迁移方案并 review 了执行，实际 DDL 由值班 DBA 执行。

```text
S  订单库要加一列，2 亿行的表，业务要求不停机。我是这块的技术负责人，
    方案是我定的，但 DDL 是值班同学在变更窗口执行的。

T  停机两小时业务不接受；直接 ALTER 会把主从延迟打高，读流量会超时。
    我要在不停机的前提下把这列加上，并且出问题能回退。

A  我写了三个方案做对比：在线 DDL 工具、影子表双写、先加可空列再回填。
    按锁影响、回滚难度、对从库延迟的冲击排了序，选了第三个。
    执行步骤、观察指标、中止条件我写成了变更清单，值班同学照着跑。
    回填那晚我在场 review，发现批次大小会让从库延迟飙到 40 秒，
    我让把批次调小、加了延迟阈值自动暂停。字段上线了，业务无感知。

R  停机 0 分钟，主从延迟峰值从改前的 40 秒压到 8 秒以内（我的变更清单记录）。
    后来这个清单被当成模板用在了另外两次大表变更上。
    我当时漏了一点：没预估回填对 IO 的影响，是值班同学提醒的。
```

**为什么这是对的**：

- 第一句就把角色边界说清了——"方案是我定的，DDL 是值班同学执行的"
- 动词全程是 `定了` / `写了` / `review` / `让调小`，没有一个字声称自己执行了 DDL
- 有一个对自己不利的细节（漏估 IO），这恰恰是可信度的来源
- 数字带口径（延迟峰值、比较基准），能在 KB 的证据里找到对应 `fact_id`

## 例 2：同一件事的 inflation 讲法（禁止）

```text
S  订单库加字段，2 亿行，要求不停机。

T  直接 ALTER 会影响线上。

A  我独立完成了整个在线变更：设计了影子表双写方案，执行了 DDL，
    回填了全部数据，把主从延迟从 40 秒优化到了 8 秒。

R  零停机完成 2 亿行大表变更，主从延迟降低 80%。
    该方案已成为团队标准模板。
```

**错在哪里**：

| 问题 | 具体 |
|---|---|
| 责任范围通胀 | "独立完成整个在线变更" + "执行了 DDL"——事实是值班同学执行的，这是 T6 Q6 必拦项 |
| 手段被替换 | 实际选的是"先加可空列再回填"，讲成了"影子表双写"——为显得更高级而改事实 |
| 数字放大 | "降低 80%" 是拿"调小批次后的 8 秒"对比"改前的 40 秒"，把一次调参的成果说成了整体变更的成果，口径被偷换 |
| 角色边界消失 | 没有"我定方案、别人执行"的说法，`oversight` 经历被讲成了 `deep` |
| 细节消失 | 漏估 IO 这个对自己不利但可信的细节没有了 |

**同样的经历，第一种讲法是 high-signal 证据，第二种是会被面试官追问三层就塌、
并且过不了 当前求职工具的证据校验 的版本。**

## 例 3：deep 级经历的正确讲法

场景：候选人自己定位并修复了线上故障。

```text
S  支付回调接口 P99 从 80ms 涨到 2s，错误率没变，第三方开始重试。

T  重试会放大流量，拖垮的不只是这一个接口。我先要止损，再定位。

A  我先在网关把这批流量切到降级返回（明确告知调用方稍后重推），
    再按"哪个接口 → 哪个依赖 → 哪批请求"逐层缩小，定位到是下游账户服务
    的连接池被占满——一个新上的批量查询没走独立池。把批量查询挪到独立池并加了超时。

R  20 分钟止损，P99 回到 90ms 左右。复盘时我们发现批量查询和生产查询
    共池这个模式还有三处，都补了独立池。
    我当时误判过一次：先怀疑是 GC，看了 GC 日志才排除，白花了 5 分钟。
```

**要点**：先止损再定位；每一步对应排除一个假设；Result 的数字可复核；
误判经历如实说。

## 例 4：historical 级——不得声称

参数表规定 `historical`（学过/用过但已过时或很浅）算 Miss，不得声称。
正确处置是显式声明，而不是含糊带过：

```text
❌ "我熟悉 Hadoop 生态，做过大数据处理。"
✅ "Hadoop 我三年前用过 MapReduce 做离线报表，之后没再碰过。
    现在的实时链路我用的是 Flink。如果这个岗位需要 HDFS 运维，我明确不会。"
```

后一句把边界划清楚。面试官对"明确说不会"的信任度远高于对"熟悉"的追问。

## 使用规则

1. **结构可学，事实不可抄。** 示例里的技术细节、数字、公司背景必须替换成候选人自己的。
2. **每个事实主张都要能落到 KB 的 `fact_id`。** 落不到就不进正式稿（T6 R3，代码校验）。
3. **角色边界先讲，再讲故事。** 第一句就说清"我做的"和"我 review / 定的"。
4. **没有证据的经历不编。** 缺故事就进 debrief 的 `待确认` 桶，问用户，不猜。
5. **`oversight` 不是弱点。** 能定方向、能 review 出问题、能担责，本身就是高级信号——
   把它讲成 hands-on 才会同时丢掉事实和可信度。
