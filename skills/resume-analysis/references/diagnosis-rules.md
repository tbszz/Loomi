# 诊断判断规则

本文件是 resume-analysis 的判断细则。SKILL.md 只定流程骨架，规则在这里。

边界先说清楚：**可枚举、可判真假的规则全部在 当前求职工具的证据校验 执行**（R1 inferred 封顶、R3 引用与数字核验、R4 跨候选污染）。本文只写需要判断力的部分，不重复代码已执行的规则。`suggestions` 每遍 ≤ 3（T9 §2 / S06）目前是 skill 侧自律规则，见 §6。

## 一、什么 annotation 值得提

一条 annotation 必须同时满足三个条件，缺一不提：

1. **可定位**：指向简历原文的一段逐字引文（`quote`），不是"整体感觉"。
2. **可判定**：说得出读者会因此产生什么误判，而不是审美偏好。
3. **可行动**：存在一个用户在不动用不存在的事实的前提下就能做的修改。

常见类别（按对读者的杀伤力排序）：

| 类别 | 判断口径 |
|---|---|
| 无可验证数字 | 结果陈述无任何量级、前后对比或验收方式。注意：没有数字本身不自动是问题——若能说明职责边界、任务复杂度、问题处理过程与验收方式，仍是有用证据（S06）。判的是"既无数字也无过程细节" |
| 无归属证据 | 陈述无法区分"我做的"和"我在场"。出现集体动词而无线索指向个人产出即命中 |
| 关键词堆砌 | 一段罗列十几个技术名词，无使用场景、无深度、无场景规模。无法区分必备与加分，读者只能按名单扫读 |
| section heading 当事实 | 见下节，单独列出因为它是最高频也最隐蔽的一类 |
| 职责边界模糊 | 同一段里角色在"参与者/负责人/评审者"之间漂移，读者无法还原个人贡献 |
| 时间线断裂或倒序不一致 | 无法判断每段经历的时长与连续性 |

不提的：

- 纯审美（字体、行距、模板）——不改变读者对候选人的判断。
- "量化、优化、突出亮点"这类空话——没有指向具体引文的建议不允许输出（T6 Q3 第 2 项）。
- 用户没有做过的工作。只诊断用户做过的事怎么写；不补造接口数、增长率、奖项、公司、技术。
- 催用户凑数：一个真实有证据的项目可以够用，不要求凑两段项目、六项技能或奖项。

## 二、severity 怎么定

sever 只取 `high` / `medium` / `low`。判据是**这个缺口会不会让读者直接误判候选人的能力或资历**，不是修改成本。

| severity | 判据 | 例 |
|---|---|---|
| `high` | 读者可能据此高估或低估候选人，且这是简历的主要卖点之一 | 主要项目里"优化系统性能，效果显著"——无指标、无手段、无前后对比 |
| `medium` | 削弱说服力，但不改变能力定性 | "参与微服务拆分"——缺个人负责的边界与产出 |
| `low` | 细节缺失，补上更好 | "负责接口开发"——缺接口规模或调用方 |

同一条简历里 high 通常不超过三条。如果到处都是 high，说明判据失效了，回到第一节重新逐条核对。

## 三、section heading 永远不是事实（硬规则）

**"熟练掌握 Java" 不是"用过 Java"。** 小节标题、技能清单、自我评价栏里的词，是候选人的自述，不是证据。

判定规则：

- heading 或技能列表里的条目，一律不进 `known_facts`，只能作为**待验证的声称**进 `to_confirm`。
- 只有正文 bullet 里带场景、带动作、带结果（或过程）的陈述，才有资格进 `known_facts`。
- 诊断这类条目时，annotation 的 `issue` 写"自述无证据支撑"，`suggestion` 指向"在哪个 bullet 里补使用场景"，而不是"把技能删掉"。
- 同一技能在 heading 与正文都有时，以正文为准，heading 不计证据。

## 四、三桶分栏（T6 Q3）

每条诊断结论必须落进且只落进一桶，不合并：

| 桶 | 放什么 | 约束 |
|---|---|---|
| `known_facts` | 简历原文直接陈述、且逐字可引用的事实 | 每条带 `quote`。heading 自述不放这里 |
| `inferred` | 从原文合理推出但原文未明说的结论 | 显式标 `[inferred]`；不得据此给高严重度断言 |
| `to_confirm` | 原文缺关键信息、需要问用户才能判定的事项 | 每个待确认项必须能落到一个具体追问 |

原文没有提到的经历、数字、成果，任何桶都不放。空桶就是空桶，不用话术填满。

## 五、confidence 分层（T11 证据置信度）

每条 annotation 带 `supported` / `partial` / `unknown` 一档：

- `supported`：缺口能被 Candidate KB 里的非 needs_review 事实直接填补。
- `partial`：KB 有相关事实但不足以支撑完整结论。
- `unknown`：KB 无相关事实，只能问用户。

**未评估是一等状态**——`unknown` 与 `— not evaluated` 如实写出，不用"整体不错"之类的总结盖住。confidence 由确定性规则聚合，不由模型自报整体分。

## 六、suggestions 的组织（T9 §2 / S06）

- 每遍最多 3 条，按"对目标岗位的价值"排序，不凑数。
- 每条三件套：`gap`（证据缺口）→ `action`（能立即执行的动作）→ `question`（一个必要追问）。
- 没有 jd_text 时按简历结构与证据质量排；有 jd_text 时优先排与 `evidence_forms` / `skill_requirements` 直接相关的缺口。
- `action` 不得要求用户提供不存在的信息——问"这个项目你负责哪部分"是追问，不是动作。

## 七、时代与环境判断

只允许有来源的时代事实，且带 `as_of` 时间标注。无来源的"当前市场冷暖"不进任何桶。参数表行业参数层（`industry_params`）里没有依据的领域，不输出趋势判断。
